# ECHO (에코) — Hyundai Pleos Connect 차량용 음성 타임캡슐 앱 개발 프롬프트

ECO와 ECHO 의 어원 잘 찾아서 의미있게 변형.


## 1. 프로젝트 개요

당신은 Android Automotive, Kotlin, Flutter, 음성 인식(STT), 음성 합성(TTS), 오디오 녹음, 차량용 UI/UX 및 현대자동차 Pleos Connect 플랫폼 개발에 전문성을 가진 시니어 소프트웨어 엔지니어입니다.

다음 요구사항을 기반으로 실제 실행 가능한 차량용 애플리케이션 **ECHO(에코)**를 개발해 주세요.

### 프로젝트 기본 정보

- 프로젝트명: ECHO
- 앱 이름: 에코
- 플랫폼: Hyundai Pleos Connect
- 주요 언어: Kotlin
- UI: Jetpack Compose 우선 검토
- 개발 환경: Android Studio
- 빌드 시스템: Gradle Kotlin DSL
- 최소 Android API: Pleos 공식 요구사항 기준
- 데이터베이스: Room
- 아키텍처: MVVM + Repository
- 비동기 처리: Kotlin Coroutines + StateFlow
- 주요 SDK: Pleos Connect SDK, TextToSpeech SDK
- 개발 방식: 기능별 모듈화 및 단계적 구현

기존 Flutter 개발 경험을 활용할 수 있도록 Flutter 연동 가능성도 검토하되, Pleos 차량 환경과 SDK 호환성이 우선입니다.

Flutter 사용을 위해 불필요하게 프로젝트 구조를 복잡하게 만들지 마세요.

### 공식 문서

- https://document.pleos.ai/docs/pleos-only/getting-started
- https://document.pleos.ai/docs/connect/guide/getting-started/application-development/setup-connect-sdk-emulator

공식 문서를 기준으로 실제 지원되는 API와 SDK를 확인하고 구현해야 합니다.

문서에서 확인되지 않은 클래스, 메서드, 라이브러리, SDK 버전을 임의로 만들어서는 안 됩니다.

## 2. 서비스 목적

ECHO는 자동차라는 개인적인 공간에서 사용자가 음성으로 추억을 기록하고, 지정한 미래의 날짜에 다시 들을 수 있도록 하는 차량용 타임캡슐 서비스입니다.

사용자는 차량 안에서 다음과 같은 경험을 할 수 있어야 합니다.

"에코야, 3년 뒤에 들을 타임캡슐 만들어줘."

"에코야, 녹음 시작해줘."

"에코야, 녹음 종료해줘."

"에코야, 저장해줘."

사용자가 기록한 실제 목소리를 미래에 다시 재생할 수 있어야 하며, 추후 가족과 공유하는 기능까지 확장할 수 있도록 설계합니다.

### 핵심 원칙

1. 음성 중심 인터페이스
2. 최소한의 화면 터치
3. 실제 사용자 목소리 원본 보존
4. 미래 날짜에 공개되는 타임캡슐
5. 자동차 디스플레이에 적합한 간결한 UI
6. 인터넷 연결 없이도 핵심 기능 사용 가능
7. 장기적인 데이터 보존과 향후 가족 공유를 고려한 설계

## 3. 핵심 기능

### 3.1 음성 호출 — "에코야"

사용자가 "에코야"라고 말하면 앱이 음성 명령 대기 상태로 전환되어야 합니다.

예시:

사용자: "에코야"

ECHO: "네, 어떤 기억을 남겨드릴까요?"

필요 기능:

- Wake Word(호출어) 감지
- 호출어 인식 후 STT 활성화
- 사용자 명령 분석
- TTS를 통한 응답
- 음성 인식 상태 표시
- 인식 실패 시 재시도
- 음성 입력 취소

호출어 인식은 STT와 별개로 구현할 수 있도록 인터페이스를 분리합니다.

Pleos 환경에서 상시 마이크 감지가 지원되는지 확인해야 합니다.

지원되지 않는 경우 화면의 마이크 버튼을 통한 음성 호출을 대체 방식으로 제공합니다.

### 3.2 타임캡슐 생성

사용자는 음성 또는 UI를 통해 새로운 타임캡슐을 생성할 수 있습니다.

생성 과정:

1. 타임캡슐 생성 요청
2. 공개 날짜 설정
3. 공개 날짜 확인
4. 녹음 시작
5. 녹음 종료
6. 저장 여부 확인
7. 타임캡슐 저장

녹음 시작 전에 반드시 공개 날짜가 결정되어야 합니다.

녹음이 완료되더라도 사용자가 저장을 승인하기 전까지 최종 저장하지 않습니다.

### 3.3 공개 날짜 설정

상대 기간과 절대 날짜를 모두 지원합니다.

상대 기간 예시:

- 1개월 뒤
- 2개월 뒤
- 3개월 뒤
- 6개월 뒤
- 1년 뒤
- 2년 뒤
- 3년 뒤
- 5년 뒤
- 10년 뒤

절대 날짜 예시:

- 2029년 11월 3일
- 내년 5월 5일
- 내년 크리스마스
- 2030년 12월 25일

음성 인식 결과를 실제 날짜로 변환해야 합니다.

예를 들어 현재 날짜가 2026년 11월 4일이라면:

"3년 뒤" → 2029년 11월 4일

"2개월 뒤" → 2027년 1월 4일

날짜 계산에는 `java.time` 사용을 우선 검토합니다.

월말, 윤년, 시간대 등 날짜 관련 예외를 처리해야 합니다.

공개 날짜는 기기의 로컬 시간대를 기준으로 계산하고 저장 시에는 시간대 정책을 명확하게 정의합니다.

### 3.4 음성 녹음

Android에서 지원하는 오디오 녹음 API를 사용합니다.

요구사항:

- 마이크 권한 처리
- 녹음 시작
- 녹음 일시정지
- 녹음 재개
- 녹음 종료
- 녹음 시간 표시
- 녹음 상태 표시
- 음성 파일 저장
- 녹음 취소
- 녹음 파일 재생

녹음 중에는 다음 명령을 지원합니다.

"에코야, 녹음 종료해줘."

"에코야, 잠깐 멈춰줘."

"에코야, 다시 시작해줘."

단, 녹음과 음성 인식이 동시에 마이크를 사용할 수 있는지는 실제 Pleos 환경에서 검증해야 합니다.

동시 사용이 불가능한 경우를 대비해 녹음 종료 버튼을 제공합니다.

원본 음성 파일을 보존하는 것이 최우선입니다.

STT 변환 결과는 원본 음성을 대체하지 않습니다.

### 3.5 타임캡슐 저장

녹음 완료 후 사용자에게 저장 여부를 확인합니다.

ECHO: "녹음이 끝났어요. 2029년 11월 4일에 열리는 타임캡슐로 저장할까요?"

사용자: "저장해줘."

ECHO: "타임캡슐을 안전하게 저장했어요. 3년 뒤에 다시 만나요."

저장 데이터:

- 타임캡슐 ID
- 제목
- 생성 날짜
- 공개 날짜
- 상태
- 음성 파일 경로
- 녹음 길이
- 사용자 ID(향후 확장)
- 수신자 ID(향후 확장)
- 음성 인식 텍스트(선택)

음성 파일은 앱 전용 저장소에 보관합니다.

장기 보관과 개인정보 보호를 고려하여 암호화 저장을 검토합니다.

### 3.6 타임캡슐 봉인

타임캡슐은 공개 날짜가 도래하기 전까지 봉인 상태를 유지합니다.

상태:

- DRAFT: 작성 중
- SEALED: 봉인됨
- UNLOCKED: 공개됨
- DELETED: 삭제됨

봉인된 타임캡슐은 제목과 공개 날짜 등 허용된 메타데이터만 표시합니다.

음성 원본은 공개 날짜 이전에 앱에서 재생할 수 없어야 합니다.

공개 날짜가 도래하면 UNLOCKED 상태로 전환합니다.

초기 버전에서는 로컬 기기 시간에 의존한다는 한계를 명시하고, 서버 기반 공개 검증은 추후 기능으로 분리합니다.

### 3.7 타임캡슐 재생

공개된 타임캡슐은 사용자가 음성 명령이나 UI를 통해 재생할 수 있습니다.

예시:

사용자: "에코야, 열린 타임캡슐 들려줘."

ECHO: "3년 전 오늘 남긴 타임캡슐이 있어요. 들려드릴까요?"

사용자: "응, 들려줘."

ECHO는 실제 사용자가 녹음했던 원본 음성을 재생합니다.

재생 기능:

- 재생
- 일시정지
- 재개
- 종료
- 재생 시간 표시
- 공개된 기록 목록

### 3.8 TTS 음성 안내

Pleos TextToSpeech SDK를 사용하여 앱의 안내 메시지를 음성으로 출력합니다.

예시:

- "어떤 기억을 남겨드릴까요?"
- "언제 다시 듣고 싶으세요?"
- "3년 뒤에 열어드릴게요."
- "녹음을 시작합니다."
- "녹음이 끝났어요."
- "타임캡슐을 저장했어요."
- "오늘 공개된 타임캡슐이 있어요."

TTS 기능은 별도의 인터페이스로 추상화합니다.

Pleos SDK가 제공되지 않는 테스트 환경에서는 Android 기본 TTS를 사용할 수 있도록 구현합니다.

실제 배포 환경에서는 공식 Pleos SDK의 지원 범위를 우선합니다.

## 5. 음성 명령 처리 아키텍처

음성 명령은 다음 구조를 사용합니다.

Wake Word Detection
→ Speech Recognition
→ Command Parsing
→ Intent Processing
→ Application Action
→ TTS Response

각 단계는 독립적으로 교체할 수 있도록 설계합니다.

### 주요 인터페이스

- `WakeWordEngine`
- `SpeechRecognitionEngine`
- `VoiceCommandParser`
- `VoiceCommandProcessor`
- `SpeechSynthesisEngine`
- `AudioRecorder`
- `AudioPlayer`
- `TimeCapsuleRepository`

### 명령 Intent 예시

- ACTIVATE_ASSISTANT
- CREATE_CAPSULE
- SET_UNLOCK_DATE
- START_RECORDING
- PAUSE_RECORDING
- RESUME_RECORDING
- STOP_RECORDING
- SAVE_CAPSULE
- CANCEL_CAPSULE
- LIST_CAPSULES
- PLAY_CAPSULE
- DELETE_CAPSULE

단순 명령은 우선 규칙 기반으로 처리합니다.

날짜 및 기간 추출도 정규식과 날짜 파서를 우선 활용합니다.

AI 모델이나 외부 LLM API는 초기 MVP에서 필수 의존성으로 사용하지 않습니다.

## 6. 데이터베이스 설계

Room 기반 로컬 데이터베이스를 사용합니다.

### TimeCapsule Entity

```kotlin
@Entity(tableName = "time_capsule")
data class TimeCapsuleEntity(
    @PrimaryKey
    val id: String,
    val title: String,
    val createdAt: Long,
    val unlockAt: Long,
    val status: String,
    val audioFilePath: String,
    val durationSeconds: Long,
    val transcript: String?,
    val ownerId: String?,
    val recipientId: String?
)
```

상태값은 Enum으로 관리하고, 데이터베이스 저장 시 타입 변환기를 사용합니다.

주요 조회:

- 전체 타임캡슐 조회
- 봉인 중인 타임캡슐 조회
- 공개된 타임캡슐 조회
- 공개 날짜가 도래한 타임캡슐 조회
- ID 기반 상세 조회

### 데이터 보존 원칙

- 녹음 원본 보존
- DB와 음성 파일 간 참조 무결성 유지
- 저장 실패 시 롤백 또는 복구
- 앱 비정상 종료 시 임시 파일 복구
- 사용자 삭제 시 관련 파일 정리
- 향후 서버 동기화를 고려한 UUID 기반 식별자 사용

## 10. 개발 시 반드시 지켜야 할 사항

1. 실제 존재하는 Pleos SDK API만 사용합니다.
2. 공식 문서에서 확인되지 않은 구현은 추측하지 않습니다.
3. SDK가 지원하지 않는 기능은 대체 구현을 제안합니다.
4. Kotlin 코드에는 불필요한 복잡성을 추가하지 않습니다.
5. MVVM, Repository, Coroutines, StateFlow를 일관되게 사용합니다.
6. 날짜 계산과 상태 전이는 단위 테스트를 작성합니다.
7. 오디오 파일 저장과 DB 저장의 일관성을 유지합니다.
8. UI는 실제 차량 디스플레이를 기준으로 설계합니다.
9. 음성 명령이 실패하더라도 터치 UI로 핵심 기능을 사용할 수 있어야 합니다.
10. 향후 가족 공유를 위해 데이터 모델의 확장성을 확보합니다.
11. 개인정보와 음성 녹음 파일을 안전하게 취급합니다.
12. 실제 실행되지 않는 가짜 SDK 코드나 더미 성공 응답을 완성된 기능으로 표시하지 않습니다.
